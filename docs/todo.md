#### 补充复现结论

- **触发条件**：仅勾选全部初审问题、输入框不填写人工补充信息时，确认初审标注可以正常通过；在输入框填写任意补充信息后再确认，才出现 `400` 及 `clothing_description has an invalid source citation`。
- **定位收敛**：问题不在“全选确认”或既有 AI 初审数据本身，而集中在 `issue_responses[].user_answer` 的处理链路。人工回答被合并到重新生成的画像字段后，对应的来源 citation 没有正确生成、持久化或转换为当前校验器认可的引用。
- **优先排查点**：人工回答映射到 `clothing_description`/衣着与随身物品相关字段时的字段归属规则；人工回答来源记录创建；citation ID 回填；草稿重建 DTO 转换；引用校验器对人工来源类型的白名单或解析逻辑。
- **验收补充**：全选且无人工回答、全选并填写一条人工回答、填写多条人工回答、只填写衣着/随身物品类回答、只填写其他类别回答，均可成功确认；每种人工回答在生成画像中均有正确内容与可解析来源。
### 【bug（环境/集成）】高德地图 JSAPI 安全代理 - `/_AMapService` 请求 504（中）

- **问题描述**：地图 JSAPI 以安全模式运行，浏览器向同源 `/_AMapService` 发出的 `convert`、`init`、`text` 请求均返回 `504 Gateway Timeout`。部署配置规定该一级路由由预览 Web 容器的 Nginx 固定代理到 `https://restapi.amap.com`，并由服务端注入 `AMAP_JSAPI_SECURITY_CODE`。因此异常发生在服务端代理到高德上游的链路，而不是浏览器直接访问高德或单一 client 的前端组件逻辑。
- **复现与证据**：
  - 前端 `LocationConfirmationPicker` 将 `window._AMapSecurityConfig.serviceHost` 设置为 `VITE_AMAP_JS_API_SERVICE_HOST`，默认值为 `/_AMapService`；
  - 项目部署说明明确：预览 Web 容器在启动时为该固定路由配置 Nginx 代理，仅转发至 `restapi.amap.com`；
  - 对部署域名 `https://main.angui.cg8.site/_AMapService/v3/ip?key=invalid` 的独立请求在 20 秒内未收到响应而超时，与页面的 504 现象一致；
  - 结论：现有证据不支持“仅本地 client 问题”。需要检查部署侧代理的 DNS、TLS、网络出口、上游可达性、超时配置和安全码注入。
- **预估工期**：0.5 人天用于部署诊断；若需调整代理、网络策略或健康检查，预计 1 人天。
- **预估难度**：中（取决于部署环境访问高德上游的网络条件和 Nginx 运行状态）。
- **预计修改范围**：
  - 预览/生产 Web 容器中 `/_AMapService` 的 Nginx location、`proxy_pass`、DNS resolver、TLS SNI、连接/读取超时设置；
  - 容器启动脚本中的 `AMAP_JSAPI_SECURITY_CODE` 注入和 Nginx 配置渲染；
  - 部署环境到 `restapi.amap.com:443` 的 DNS 解析、IPv4/IPv6 路由、防火墙或 HTTPS 代理策略；
  - 可选的代理健康检查、结构化错误日志和前端地图不可用时的降级提示。
- **修改要点**：
  1. 在 Web 容器内分别验证 DNS 解析、TLS 握手和对 `https://restapi.amap.com` 的请求，记录失败阶段；
  2. 检查 `/_AMapService/` 是否保留一级路径、转发时是否正确去除前缀并附加 `jscode`，以及是否将 Host/SNI 指向高德上游；
  3. 检查实际 Nginx error log 的 upstream timeout、resolver、connect/read timeout 记录；
  4. 若为高德短暂上游故障，增加监控、可观测日志和前端可重试/手工填写降级，不把短暂故障误修为客户端代码；
  5. 若为部署网络或配置问题，修复代理链路后保留安全模式，不能回退为将 `securityJsCode` 暴露给浏览器。
- **最终验收标准**：
  - 从部署 Web 容器和至少一个外部浏览器网络分别访问地图，`/_AMapService` 的 `init`、`text`、`convert` 相关请求均不再返回 504；
  - 地图初始化、地点检索、坐标转换和逆地理编码可稳定完成，错误日志中无 upstream timeout；
  - 安全码仅存在于服务端/代理环境变量，前端产物和浏览器网络请求中不泄露 `AMAP_JSAPI_SECURITY_CODE`；
  - 高德或代理暂时不可用时，页面给出可理解的地图服务不可用提示，并保留手工填写地点的业务路径；
  - 若连续多次跨网络探测均正常，且确认历史故障为上游临时事故，可将本事项标记为“已恢复/无需代码修改”，保留事故记录和监控结论。

### 【feature】协作空间 - 基于 WebRTC 的低延迟语音对讲（PTT）（高）

- **需求描述**：在案件协作空间中提供授权成员间的实时语音对讲，形态类似现场对讲机。成员按住发言按钮（Push-to-Talk，PTT）开始采集和传输麦克风音频，松开即停止；指挥人员可发起更高优先级的指挥广播。该能力用于实时现场调度，不是文字聊天、语音文件上传或轮询刷新。
- **明确技术边界**：
  - 不采用轮询作为实时通信方案；现有每 8 秒空间事件轮询不能用于语音对讲；
  - 不将 Webhook 用作浏览器实时通信。Webhook 仅适合服务器向外部系统的异步通知，无法承载交互式会话或低延迟媒体；
  - 使用 **WebSocket** 作为实时信令、会话鉴权、成员在线状态、PTT 发言状态、ICE candidate 交换和重连控制通道；
  - 使用 **WebRTC 音频轨道** 传输实时媒体，依赖 DTLS-SRTP 加密；不能通过 WebSocket 直接传输音频流；
  - 三人及以上的协作空间使用 SFU（Selective Forwarding Unit）转发媒体，避免浏览器 Mesh P2P 的带宽和连接数随成员数平方增长；部署 TURN/STUN（优先自建 `coturn`）保障受限网络和 NAT 环境下的接入。
- **预估工期**：14 人天
- **预估难度**：高
- **技术选型与实施前置决策**：
  - 优先评估成熟的可自托管 WebRTC SFU，例如 **LiveKit**，采用其服务端、React/TypeScript SDK、短时房间令牌和监控能力；不建议在本项目中从零实现 RTP、拥塞控制、SFU 或 NAT 穿透；
  - 后端 Rust 服务负责复用既有案件角色和协作空间成员权限，签发短时、空间绑定、最小权限的 SFU/信令访问令牌，并接收经过鉴权的连接/断开/发言状态；
  - 部署方负责 SFU、TURN、TLS/WSS、UDP 端口段、带宽配额和指标。若部署环境无法开放 UDP，必须验证 TCP/TLS TURN 降级质量并明确容量限制；
  - 一期默认不录音、不保存实时音频内容。若未来需要录音、转写或证据留存，必须单独取得业务/隐私授权，定义存储、保留期限、访问权限、导出和审计要求，不能随语音对讲一并默认启用。
- **预计修改范围**：
  - 后端协作空间权限与令牌接口：`src/api/routes/collaboration_spaces.rs`、`src/application/services/collaboration_space_service.rs`、认证中间件和 API 模型；
  - 新增语音会话/令牌状态、PTT 事件、可选的空间语音策略与审计事件实体、迁移和服务；
  - WebSocket 信令端点、连接生命周期、事件广播、速率限制与服务端指标；
  - 前端协作空间面板：`frontend/src/components/CollaborationSpacePanel.tsx`、`frontend/src/components/CollaborationActivityPanel.tsx`，新增语音对讲面板、WebRTC/SFU 客户端 hook、麦克风权限与音频输出控制；
  - WebSocket/SFU/TURN 部署清单、Nginx/Traefik 长连接与 Upgrade 配置、TLS、UDP/TCP 端口、环境变量、容器编排、监控和告警；
  - 协作空间消息、语音报告与位置共享的现有能力需要与实时语音 UI 协调，但不应被移除。
- **修改要点**：
  1. 仅在用户已认证、仍持有案件允许角色、协作空间处于 active 状态且用户为 active 成员时签发短时语音令牌；离开空间、空间归档、角色撤销、会话吊销或账号停用后立即拒绝续期并强制断开；
  2. PTT 控制必须支持鼠标/触控长按和键盘无障碍操作，默认静音；清晰展示“正在连接、可发言、正在说话、他人正在说话、麦克风权限被拒绝、网络较差、重连中、已断开”等状态；
  3. 定义发言仲裁策略：一期建议单空间单个普通发言者，指挥广播具备可见的高优先级并可打断普通发言；多人抢话时按服务端授予的 floor token 排队/提示，客户端不得自行伪造发言状态；
  4. 采集音频启用回声消除、自动增益和降噪；提供听筒/扬声器输出、音量、静音和设备选择；禁止自动播放未获用户交互许可的音频，遵循浏览器 autoplay 政策；
  5. 使用 Opus 音频编码及 WebRTC 自适应码率/丢包恢复能力；根据网络质量提示降级，而非反复创建房间或改用轮询；
  6. WebSocket 连接只发送信令与轻量控制事件，必须有心跳、指数退避重连和恢复后的空间成员/发言状态同步；音频重连与信令重连分开处理，避免重连风暴；
  7. 音频媒体通过 WebRTC 的 DTLS-SRTP 加密，信令走 WSS，TURN 使用长期凭据机制或短期签名凭据；令牌、ICE 凭据、候选地址和用户精确位置不得写入前端日志、通用审计详情或错误上报；
  8. 限制每空间最大在线成员、每用户并发音频会话、令牌签发频率和 PTT 切换频率；对慢客户端、SFU 负载、TURN 带宽和异常重连建立背压/熔断与告警；
  9. 复用现有语音报告上传作为实时通信不可用时的异步替代，并在 UI 中明确区分“实时对讲”和“发送语音报告”。
- **性能与通信效果指标**：
  - 正常网络和同地域部署下，按下 PTT 到其他在线成员听到首帧音频的端到端延迟 `p95 <= 800 ms`，稳定说话阶段的单向音频延迟 `p95 <= 500 ms`；
  - PTT 松开后 `<= 500 ms` 停止上行音频，其他成员界面同步取消发言状态；
  - 网络短暂中断后，在网络恢复 `10 秒` 内自动重新建立信令与媒体连接；
  - 在至少 20 名在线成员、其中 1 名普通发言者或 1 名指挥广播者的单空间压力场景下，持续 10 分钟满足延迟目标且无明显音频断续；最终容量须根据 SFU/TURN 服务器规格压测确定；
  - 连接和媒体质量指标至少包括：连接成功率、加入耗时、首帧耗时、往返时延、jitter、丢包率、重连次数、音频轨道订阅数、SFU CPU/内存/出口带宽和 TURN 中继流量。
- **最终验收标准**：
  - 两名已授权且已加入同一 active 协作空间的用户，在 Chrome/Edge 和常见移动浏览器中可完成麦克风授权、加入语音房间和 PTT 实时对讲；无需刷新页面、轮询或上传音频文件；
  - 语音媒体走 WebRTC，浏览器网络面板可见 WSS 信令及 WebRTC 连接，不出现以 WebSocket/HTTP 轮询传输音频数据的实现；
  - 三人及以上加入时通过 SFU 稳定收听，不因 Mesh P2P 造成明显带宽激增或连接失败；在需要中继的网络环境下可通过 TURN 建连；
  - 普通发言、多人抢话、指挥广播优先级、松开发言、静音、设备切换、麦克风拒绝、扬声器不可用、网络降级与断线重连均有明确且无障碍的界面反馈；
  - 未授权用户、家属角色、未加入成员、离开成员、已归档空间成员、会话被撤销账户不能申请令牌、连接、发布或订阅任何空间音频；
  - 实时音频不被默认录制或持久化；所有加入、离开、令牌签发、发言开始/结束、广播与权限拒绝事件均写入不含音频内容的审计记录；
  - 在定义的并发与弱网压测中满足 PTT 首帧和稳定音频延迟目标，并且现有协作空间、文字消息、位置同意与撤回、地图、语音报告、归档和案件权限流程回归通过。

### 【enhance】线索 AI 提取与审核 - `action_candidates` 语义错误、Prompt 约束不足（高）

- **问题描述**：对“有人说昨天下午三点多老人出现在学校东门门口”的线索，AI 将“出现在”提取为 `action_candidates`。该语义不符合业务定义：这是一条“目击/出现事件”，而不是人物执行的可归类行动。错误动作候选会影响后续的线索筛选、行动轨迹判断、任务派发和统计。同时审核页暴露了未翻译的内部 Schema 字段（如 `action_candidates`、`content_summary`、`location_text`、`occurred_at`、`source_text`）和英文未审核提示，且同一信息被摘要、候选字段和原始字段重复展示，增加人工审核负担。

- **预估难度**：中
- **预计修改范围**：

- **Prompt 优化要点**：
  1. 在系统 prompt 中将“事件类型”和“人物动作”严格分离。`sighting/目击出现`、`last_seen/最后出现`、`contact/接触`、`location_update/地点更新`、`phone_record/通话记录`、`field_feedback/现场反馈` 等属于线索事件类型；`action_candidates` 仅允许填写可观察、可区分的主动行为，例如“步行”“乘坐公交”“进入/离开某建筑”“与某人同行”“购买物品”“停留”等；
  2. 明确禁止将“出现、目击、发现、有人说、得知、疑似、位于、在某地”等状态词、报告词、来源词或地点介词写入 `action_candidates`。没有足够动作证据时必须输出空数组 `[]`，不能为了填满字段进行猜测；
  3. 新增结构化 `event_type` 与 `event_summary` 字段。对本例应输出：`event_type: "sighting"`，动作候选为空，时间候选为“昨天下午三点多”，地点候选为“学校东门门口”，来源片段保留原文；
  4. 在 prompt 中要求只提取原文明确支持的信息，区分“原文事实”“推断/待核实”“未提供”；时间相对表达保留原文并尽可能解析为基于案件基准时间的候选绝对时间，解析不确定时标记待确认；
  5. 为每个候选字段返回证据片段、置信度和是否需人工确认。禁止模型生成原文没有出现的人物、交通工具、动作、地址精度或因果关系；
  6. 提供覆盖目击、电话记录、现场反馈、多人叙述、模糊时间、否定信息、无动作信息及多动作信息的中文 few-shot 样例，并增加输出 JSON Schema 校验与语义后校验；
  7. 增加规则兜底：若 `action_candidates` 命中禁止词、只有状态词，或在原文中没有动作证据，则清空候选并保留人工审核提示；规则不能将不确定文本强行改写为具体动作；
  8. 审核界面只展示对审核决策有意义的中文字段：线索事件、原始内容、时间候选、地点候选、来源片段、可选动作、置信度和待确认原因。内部字段名、原始 JSON 和英文模型提示仅在受控调试视图可见；相同内容仅展示一次。
- **最终验收标准**：
  - 对截图示例生成的候选线索被分类为“目击/出现事件”，`action_candidates` 为空，不再把“出现在”作为动作；时间、地点和来源均能追溯到原始文本，并被标记为需要人工核实；
  - 对包含明确行为的文本，例如“老人独自乘坐 3 路公交离开学校东门”，事件类型正确，动作候选可提取“乘坐公交”“离开”，且每一候选均有可定位的原文证据；
  - 对没有明确动作、含有否定词、含相对时间或描述模糊的输入，模型不会臆造动作和精确事实，而是输出空候选或待确认项；
  - 结构化输出未通过 JSON Schema、证据一致性或禁止词校验时，系统不会生成可直接接受的错误候选，并显示可理解的中文审核提示；
  - 审核页面不再展示英文未审核提示和内部 snake_case 字段；关键字段不重复堆叠，人工可在单屏完成接受、修订或拒绝；
  - 接受候选后创建的正式线索、地图标记、线索筛选、任务关联和审计记录正确使用事件类型与经确认的动作字段，现有线索来源/权限流程回归通过。
### 【bug/enhance】线索排除审核 - 排除动作被长耗时 AI 链路拖慢，应改为非阻塞 AI 建议（高）

- **问题描述**：指挥端对待审核线索执行“排除”时等待时间过长。抓包观察到审核过程中存在 AI 请求；但最终无论 AI 请求是否给出结果，线索仍会被直接改为“已排除”。这使人工已明确决定的审核操作被不确定、耗时的 AI 链路拖慢，且用户无法理解等待原因或利用 AI 结果。现有审核弹窗仅提示状态变更和审计记录，未展示 AI 对排除决定的支持/反对意见、证据依据或风险提醒。

  - 新增 AI 审核建议数据模型、接口、Prompt、异步执行、结果缓存、过期/失败状态与可观测性；

  - 当前允许的摘要状态转移为：`draft -> submit -> pending_review`、`pending_review -> publish/reject`、`published -> withdraw`。已驳回、已发布、已撤回或已被替代的版本不能再次发布，重复/过期请求会返回该 409。

  5. 将状态机定义为服务端唯一事实，并在响应中返回 `allowed_actions`/`can_publish`。前端只对当前版本允许的动作展示按钮；禁止对已发布、已驳回、已撤回、superseded 或旧版本发送发布请求；
  6. 发布采用版本号/状态的乐观并发控制（例如携带 `expected_version` 或实体 revision），发现版本已变化时返回可理解的“版本已更新，请重新加载”，而不是泛化 409；发布成功后明确标记其他 published 为 superseded，并刷新当前版本链；
  7. 驳回后提供“基于此版本修订”入口，默认带入原正文和父版本关系；新版本的审核页显示“修订自 vN、驳回理由、修改内容”和 diff，避免人工误以为是无来源的新版本；
  8. 发布失败、重复点击、请求超时或页面刷新后，前端恢复到服务端真实状态，不清空当前编辑内容，不重复创建版本；
  9. 审计每次 AI 生成、手工创建、提交、驳回、修订、发布、撤回和 supersede，记录版本链、操作者、理由和结果，但不把完整敏感摘要写入通用日志。
- **最终验收标准**：
  - 指挥人员可从摘要区域打开当前版本和任意历史版本详情，看到正文、来源、生成方式、父版本、状态、审核理由、时间线及当前允许操作；
  - 页面明确区分“AI 重新生成”和“手工创建/编辑草稿”，手工内容不会被标注或展示为 AI 生成；
  - 驳回 v2 后通过“基于 v2 修订”生成的新版本可追溯到 v2，版本页显示修订关系、修改差异和驳回理由；版本号可连续递增但不丢失父子链与生成来源；
  - 只有处于 `pending_review` 且 `publication_eligible=true` 的当前版本可以发布；前端不会对其他状态版本展示发布按钮，重复/过期发布会返回明确的状态冲突提示并自动刷新；
  - 发布成功后当前版本为 `published`，旧已发布版本变为 `superseded`，志愿者只能读取符合可见性策略的已发布版本；
  - 模拟重复点击、双标签页、旧页面发布、驳回后重复发布、发布后刷新、AI 生成失败和手工草稿提交等场景，不再出现无法解释的 409，且不会重复创建版本或丢失编辑内容；
  - 摘要版本查看、diff、提交审核、驳回、修订、发布、撤回、权限隔离、来源范围、脱敏校验和审计回归测试通过。
### 【enhance】任务区域资源检索 - 搜索中心固定取首个地点，需支持选择及用户指定地点（中高）

- **问题描述**：指挥端“任务区域周边资源”当前只有资源类别选择，未提供检索中心选择。服务端在未传入浏览器坐标时，会从可见任务中取第一个带坐标的任务；若无任务坐标，再从已确认地点中取排序结果的第一个地点。这样搜索中心实际上受列表顺序影响，无法针对当前行动目标选择其他已确认地点，也无法让用户临时指定一个搜索地点。
- **已核实的代码事实**：
  - 前端 `listCasePois` API 已支持可选 `browser_longitude`/`browser_latitude`，但指挥端当前调用 `listCasePois(token, detail.id, poiCategory)` 时未传入中心参数；
  - 后端 `poi_search_center` 支持成对的浏览器坐标，并会先转换为高德坐标；未传坐标时进入 `authorized_center`，按任务坐标或确认地点的首条记录回退；
  - 现有设计明确不持久化临时浏览器坐标，且需要遵守案件角色、地点可见性和坐标隐私限制，这些安全边界应保持不变。
- **预估工期**：2.5 人天
- **预估难度**：中高
- **预计修改范围**：
  - 指挥端任务区域资源检索区：`frontend/src/pages/CaseWorkspacePage.tsx`，增加搜索中心来源、已确认地点选择、地图选点/地址检索和当前中心反馈；
  - 前端 API 与类型：`frontend/src/api/cases.ts`，扩展中心参数、中心来源和校验错误处理；
  - 后端案件 POI 查询模型与服务：`src/api/models.rs`、`src/application/services/case_collaboration_service.rs`、`src/api/routes/cases.rs`，支持地点 ID 或临时坐标的安全解析；
  - 已确认地点/任务坐标查询、权限过滤、地址解析与高德坐标转换；
  - OpenAPI、审计/指标、前端单元测试、接口集成测试和地图/弱网回归。
- **修改要点**：
  1. 提供明确的“检索中心”选择器，至少包含“任务默认中心”、每个有坐标的已确认地点、 “使用我的当前位置”和“指定地点”四类选项；不得静默取列表第一项；
  2. 选择已确认地点时传递受服务端校验的 `place_id` 或等价稳定标识，由服务端确认该地点属于案件、状态为 confirmed、调用者有可见权限且包含有效坐标；不能信任前端直接提交的任意坐标替代地点权限校验；
  3. “使用我的当前位置”只作为本次查询的临时 WGS-84 坐标，服务端转换为高德坐标后立即使用，不写入案件、地点、审计详情或长期缓存；明确显示定位权限和隐私提示；
  4. “指定地点”支持用户输入地址并通过受控地理编码得到候选地点，或在地图上点选临时中心。候选需显示地址、坐标精度/来源和确认按钮；未经用户确认不得发起查询；临时中心默认仅对当前请求有效；
  5. 保留无中心参数时的服务端默认策略作为兼容回退，但响应必须返回 `center_source`、可读的中心描述和是否为默认回退；服务端不再依赖未定义的数据库排序作为用户不可见的唯一决策；
  6. 对中心坐标范围、地理编码失败、地点无坐标、地点已撤回/非公开、定位拒绝和高德转换失败提供明确提示；不得回退到未经授权的案件内部地点；
  7. 查询结果卡片显示“本次检索中心：xxx”，切换中心或案件后清空旧结果，避免用户误以为结果来自新中心；可选支持保存为案件地点必须走独立的“补充地点”审核流程，不能在查询动作中隐式保存；
  8. 继续使用现有 POI 选择 token 和路线规划权限边界；临时搜索中心不改变 POI 目的地的选择、路线和坐标隐私规则。
- **最终验收标准**：
  - 指挥人员可以在任务默认中心、任一有权限的已确认地点、本人当前位置和用户指定地点之间切换，并在查询前看到当前中心名称/来源；不再无提示地固定使用地点列表第一项；
  - 选择不同中心查询同一类别时，服务端请求和返回结果的 `center_source` 与界面展示一致，旧结果不会残留；
  - 指定地点必须经过地址/地图确认，服务端完成坐标有效性、案件范围和权限校验；临时坐标不会写入案件地点、审计正文或长期存储；
  - 志愿者只能选择其有权查看的公开/确认地点，指挥人员可按角色看到授权范围内的内部地点；未授权、撤回、无坐标地点无法作为检索中心；
  - 定位拒绝、地理编码无结果、坐标转换失败、地图服务不可用和网络超时均有可理解的降级提示，并可回到任务默认中心或手工输入；
  - 查询结果、POI 选择 token、路线规划和现有任务/地点补充审核流程回归通过，相关 API、权限、坐标不持久化和地图隐私测试通过。
